## 1. Supplementary Payment Fee Display & Enforcement

### Problem

When applications were reverted by DTDO for category/payment-term corrections (e.g., from 1-year Silver ₹8,100 to 3-year Silver ₹13,500), the following issues were observed:

| Issue | Description |
|-------|-------------|
| **Fee display confusion** | The applicant's Step 5 (Fee Calculation) page showed the **full new fee** (₹13,500) without making it clear that ₹8,100 was already paid. Only the next page (payment page) showed the supplementary ₹5,400 breakdown. |
| **Payment bypass** | In some cases, clicking "Pay ₹13,500" completed the submission without actually charging the ₹5,400 difference, because the payment status was already `paid` from the initial payment. |
| **Missing `previous_total_fee`** | The `previous_total_fee` column was not being correctly populated during the revert process, causing the supplementary amount calculation to fail. |

### Root Cause

When applications were manually reverted via scripts (yesterday's session), the `previous_total_fee` was not set. Additionally, the code path for `payment_pending` status with `payment_status = 'paid'` was incorrectly allowing submission bypass.

### Fixes Applied

| Fix | Description |
|-----|-------------|
| **Fee breakdown on Step 5** | Added a clear breakdown showing: New Total Fee, Previously Paid Amount, and **Supplementary Due** (highlighted in amber). |
| **Payment page clarity** | Added prominent display of previously paid amount alongside the supplementary due on the HimKosh payment initiation page. |
| **Server-side enforcement** | HimKosh routes now correctly calculate `actualAmount = totalFee - previousTotalFee` for supplementary payments, with server-side validation preventing zero-amount bypasses. |
| **Data repair** | SQL script provided to set `previous_total_fee = 8100` on the 4 affected Kullu applications (HP-HS-2026-KUL-000236, 000311, 000362, 000306). |

### Affected Files

| File | Change |
|------|--------|
| `client/src/pages/applications/new.tsx` | Fee breakdown display on Step 5 |
| `client/src/pages/payment-verification.tsx` | Supplementary fee info on payment page |
| `server/himkosh/routes.ts` | Server-side supplementary amount calculation |
| `shared/schema.ts` | `da_recommendation` column addition |

## 2. RC Certificate Preview Button

### Problem

DTDOs had to **download** the RC certificate PDF every time they wanted to check it. This cluttered their downloads folder and was slow for repeated verification.

### Solution

Added a new **"Preview RC Certificate"** button that opens the certificate PDF in a new browser tab.

| Component | Change |
|-----------|--------|
| **Certificate Generator** (`client/src/lib/certificateGenerator.ts`) | New `previewCertificatePDF()` export — reuses the same rendering engine but opens in a new tab via `window.open()` instead of triggering download. |
| **DTDO Review Page** (`client/src/pages/dtdo/application-review.tsx`) | Added 👁 **Preview RC Certificate** (primary button) alongside ⬇ **Download RC Certificate** (outline button). |

### User Experience

- **Preview** — Opens certificate in new tab instantly. No download clutter.
- **Download** — Saves the file as before (unchanged behavior).
- Both buttons share loading state to prevent double-clicks.

## 3. DA "Recommend Rejection" Workflow

### Problem

Currently, the DA can only forward an application to DTDO after verifying **all uploaded documents**. In practice, some applications are obviously reject-worthy (e.g., fake/forged documents, ineligible property, blatant non-compliance). The DA was forced to:

1. Mark all documents as "Verified" (which is incorrect — they shouldn't approve fake docs)
2. Forward to DTDO
3. DTDO then rejects

This created a false paper trail where the DA appeared to have verified fraudulent documents.

### Solution

New **"Recommend Rejection"** button on the DA application detail page.

#### Workflow

```
DA opens application
    ├── Normal path: Verify all docs → Forward to DTDO ✅
    │
    └── New path: Click "Recommend Rejection" → Provide rejection reason (min 20 chars)
                  → Application forwarded to DTDO with rejection tag
                  → DTDO sees red banner: "⚠️ DA Recommends Rejection"
                  → DTDO can Accept (override), Reject, or Revert as usual
```

#### Implementation Details

| Component | Change |
|-----------|--------|
| **Schema** (`shared/schema.ts`) | New `da_recommendation` column (`varchar(20)`, nullable). Values: `null` (normal), `'reject'` (recommend rejection). |
| **Backend** (`server/routes/da.ts`) | Modified `forward-to-dtdo` route to accept optional `recommendation` field. When `recommendation === 'reject'`, document verification is **bypassed**. |
| **DA UI** (`client/src/pages/da/application-detail.tsx`) | New red "Recommend Rejection" button with confirmation dialog requiring minimum 20-character explanation. |
| **DTDO UI** (`client/src/pages/dtdo/application-review.tsx`) | Red bordered banner at top when `daRecommendation === 'reject'`, showing DA's rejection reason. Normal blue DA Scrutiny Report card is hidden when rejection recommendation is present. |
| **Audit Trail** | Action logged as `forwarded_to_dtdo_recommend_reject` with remarks prefixed `[DA RECOMMENDS REJECTION]`. |

#### Key Design Decisions

1. **No separate status** — The application still moves to `forwarded_to_dtdo`. This keeps the pipeline simple and doesn't require new queue/tab logic.
2. **DTDO has final authority** — The recommendation is advisory only. DTDO can accept, override, or revert regardless.
3. **Document bypass is intentional** — There's no point verifying documents that the DA believes are fraudulent. The bypass prevents false verification records.
4. **Mandatory explanation** — DA must provide at least 20 characters explaining why they recommend rejection. This ensures accountability.

### Database Migration Required

```sql
-- Add da_recommendation column (will be handled by db:push)
ALTER TABLE homestay_applications ADD COLUMN IF NOT EXISTS da_recommendation VARCHAR(20);
```

This column is automatically managed by Drizzle ORM. Running `npm run db:push` on deployment will add it.
