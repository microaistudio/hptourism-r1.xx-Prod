## 1. The Renewal Pipeline

### Problem
Previously, existing RC holders were forced to use the "New Registration" pipeline or the "Legacy Onboarding" pipeline, which required irrelevant documents (like Revenue Papers) and didn't clearly link their new digital RC with their previous paper license.

### Fixes Applied / Workflow
- **Pre-Qualification Gate (`existing-owner-onboarding.tsx`)**: The system now asks existing owners for their paper RC number, Issue Date, and Expiry Period.
  - If the RC is expired, or within the configured expiration threshold, it automatically blocks Legacy Onboarding and presents an amber alert: **"Proceed to Renewal Pipeline"**.
- **Configurable Renewal Window**: The former hardcoded 90-day limitation has been decoupled. Administrators can now adjust the exact threshold (e.g., 90 days) dynamically through the Admin Policy Settings UI based on state guidelines.
- **Dedicated Route (`renewal.tsx`)**: The user is redirected to a tailored application form (`/applications/renewal`).
- **Required Documents Adjustments**: The `isRenewal` flag dynamically hides the requirement for "Revenue Papers" (Jamabandi/Tatima), leaving only Affidavits, Form-C, and Photos as mandatory uploads.
- **Backend Schema (`owner.ts`)**: The backend now strictly accepts `applicationKind: "renewal"` and safely records the paper RC number as `parentCertificateNumber` inside the database to maintain audit lineage.
- **Fees**: Renewal currently utilizes the exact same fee structure logic as new registrations, seamlessly integrating with HimKosh.

## 2. Dynamic Workflows & Feature Set Expansion

With v1.4.0, several extensive application requirements and administrative workflows were introduced to round out the core application model:

### 2.1 Front-End Application Dynamism
- **Approved Map Document Integration**: A new document block was added for new applicants. Understanding this is a soft requirement, operators are enforced to make a logical choice: either upload the approved building map, OR check the automated **"Not Applicable (NA)"** box and provide an optional comment. This avoids breaking database structures through JSONB storage encapsulation.
- **Urban vs Rural Zone Logic**: The system dynamically flags Municipal Corporation (MC) boundaries versus Gram Panchayats. Workflows were adjusted to conditionally demand specific localized documents (such as MC NOCs or Structural Plans) depending squarely on property jurisdiction.

### 2.2 Payment Infrastructure & Reconciliation
To address firewall synchronization issues with the Himkosh state gateway, a highly resilient **3-Layer Reconciliation Strategy** was established:
1. **Layer 1 (Cron Engine)**: Scans pending/stranded transactions in the background and proactively probes Himkosh APIs for updates.
2. **Layer 2 (Page-Load Strategy)**: Enforces real-time gateway checks whenever an applicant visits their dashboard (bypassing reliance solely on server-to-server callbacks).
3. **Layer 3 (Manual Resolution)**: Integrated the dedicated **`payment_officer`** role, armed with a UI dashboard specifically mapped for resolving edge-case payment discrepancies.

### 2.3 Field Inspection Optimization
- **Dedicated Inspector Role (`inspector`)**: Created an isolated role separated from the DA and DTDO hierarchies. Districts can now assign multiple authorized inspectors for horizontal scaling and accountability.
- **Rich Metric Capture**: The inspection reporting payload was vastly upgraded to demand explicitly tallied room data (Single beds, Double beds, Family subsets) and related inspector notes, streamlining certificate generation.
- **AADHAAR Security**: Added a unified physical toggle to confirm Aadhaar verification during the site review.
- **Configurable Backdating**: System Administrators can configure exactly how many days in the past a site inspection date can be logged, averting audit anomalies.
- **Data Discoverability**: Formulated a standardized Drill-Down Search engine, granting Supervisors and Operations teams multi-axis filtering across thousands of applications.

## 3. Solution Architecture & Port Configuration

Below is the definitive port mapping for the Homestay application. If the machine needs to be migrated or subjected to firewall audits, these are the sole dependencies.

| Component | Default Port | Internal / External | Description |
|-----------|--------------|---------------------|-------------|
| **Nginx (Reverse Proxy)** | `80` (HTTP) | External | Public HTTP traffic (redirects to HTTPS). |
| **Nginx (Reverse Proxy)** | `443` (HTTPS) | External | Public HTTPS traffic and HimKosh callback reception. |
| **Node.js (PM2)** | `5055` | Internal | The primary web server. `nginx` proxies traffic here. |
| **PostgreSQL** | `5432` | Internal | The relational database. Must remain closed to external traffic. |

### Note on Large Files & Server Stability
Files such as `new.tsx` (4,200+ lines) and `owner.ts` (1,800+ lines) have grown significantly large.
- **Performance Impact (Zero Risk):** These file sizes have *no impact* on server starvation, load capacity, or CPU limits. A 2,000-line route is parsed once into server memory at boot. The volume of simultaneous web requests is constrained by Database Connections or Network Bandwidth, not file length.
- **Maintainability Impact:** The sole risk is developer error (human mistake) due to navigating large files.

## 4. Fortification Action Plan (v1.4.0 Completion)

Given the impending election lock-down period (late May onwards), major framework structural rewrites (like splitting files into hooks and backend services) represent an unacceptable risk to portal stability. 

Therefore, Version 1.4.0 officially includes the **Fortification Strategy**, comprised of two 100% safe initiatives:

### Action 1: Automated End-to-End (E2E) Testing
- **What:** Configure Playwright or Cypress to automate the actions of "Virtual Users."
- **Why:** To mechanically verify that New Registrations, Renewals, and Service Requests function flawlessly without manual clicking. It ensures NO REGRESSIONS enter the production environment during minor updates.
- **Safety:** It modifies zero lines of the production web server logic.

### Action 2: Tactical Cleanup & Waste Removal
- **What:** A comprehensive pass over the codebase to remove unused variables, delete dead/commented code, strip out obsolete `console.logs`, and annotate complex logic blocks. 
- **Why:** Cleans up the developer experience without moving core logic around, guaranteeing current runtime behaviors remain untouched.
